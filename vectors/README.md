# Conformance vectors

Every reader of the release format, in any language, must report the expected result code for every
case here. The files are generated by `tools/make_vectors.py`; never edit them by hand.

## Files

- `vectors.json`: the cases.
- `keyring.json`: the signing keys every case is checked against.
- `test-keys.json`: the private keys behind them, and the recipient keys installers hold. **Test
  keys only:** they are public, so nothing may ever trust them.
- `<case>.prel`: one release file per case.

## A case

```json
{
  "name": "requirement-at-max",
  "file": "requirement-at-max.prel",
  "expected": "REQUIREMENT_NOT_MET",
  "description": "System requirement at max_exclusive.",
  "context": {
    "checks": "installer",
    "accept_test": false,
    "component": "example.unit.app",
    "hardware": "example-hw-a",
    "route": "relay",
    "installed": {
      "unit": { "example.unit.app": "1.5.0", "example.unit.boot": "1.2.0" },
      "system": { "example.parent.app": "4.0.0" }
    },
    "payload_types": ["raw-bin"],
    "recipient_keys": ["vec-device"],
    "reinstall": false,
    "allow_downgrade": false
  }
}
```

`context` is what the reader is told about its target, as in `release-format.md` section 7:

| Field | Meaning |
| --- | --- |
| `checks` | `"verifier"` runs steps 1–5, `"host"` steps 1–12, `"installer"` every step. |
| `accept_test` | Whether `test` releases are accepted (step 6). |
| `component`, `hardware`, `route` | The target component, the unit's hardware ID and the route in use (steps 7–9). |
| `installed` | Installed versions by scope; a missing component is an unknown version (steps 10–11). |
| `payload_types` | Payload types the installer knows (step 12). |
| `recipient_keys` | IDs of the recipient keys the installer holds; the private keys are in `test-keys.json` (step 13). |
| `reinstall`, `allow_downgrade` | The caller's flags (step 11). |

A reader that only implements part of the format, such as PelcoHub's upload check, runs the cases
whose `checks` it supports, plus the installer cases that fail by step 5, which it must report the
same way.

Each case has exactly one fault, so the expected code doesn't depend on how a reader orders checks
within a step.

## Regenerating

```bash
python tools/make_vectors.py          # rewrite vectors/
python tools/make_vectors.py --check  # what CI runs
```

Every random value is derived from the case name, so regenerating changes only the cases whose
definitions changed. A new case means a change to the generator, never a hand-made file.
